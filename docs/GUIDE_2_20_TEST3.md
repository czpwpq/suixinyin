# 2.20-test3 · 激活等待与启动核验修复

用户2.20-test2诊断已证实配对成功、无线ADB能连接；一次内置服务交付等待18秒超时，另外两次离开激活页后被取消。这些尝试尚未进入NFC，不能归因于手机壳供电或图片内容。旧版吞掉启动输出，现有诊断不足以确定具体启动异常。

## 这次如何使用

1. **直接覆盖安装，不要先卸载。** 已有本机配对密钥可保留，通常不需要重新执行配对。
2. 进入「设备 → 内置激活」，使用系统无线调试首页当前的连接端口，点击第③步激活。端口可能改变，不要一直使用旧截图里的数字。
3. 状态卡现在固定在页面顶部，能看到连接、启动、交付与复验阶段。Android的“已连接到无线调试”只表示第一层ADB通道，**必须等随心印显示“内置服务已激活”**才能推图。
4. 激活期间按返回会让你选择继续等待或明确取消；短暂切换页面由限时前台服务继续处理，不会仅因Activity.onStop自动取消。随时可明确取消，不自动刷屏。
5. 看到“内置服务已激活”后，返回照片或阅读页再明确发送/连接。此时服务已通过断开启动ADB后的身份与存活复验。

如果仍失败，请复制「激活诊断」全文。最下面新增「启动阶段（已脱敏）」能区分Shell没有启动、app_process/类加载、Context、Provider、交付及断开ADB后退出等问题，不再只有等待超时。**不要重新发送配对码。**

## 代码改动

- 固定顶部状态和进度，明确ADB连接与授权服务就绪的区别，返回防误取消。
- 用户主动激活时启用短前台服务，最长约一分钟；完成、取消、失败、超时都结束，不永久保活。
- 使用Shell内建trap/export/exec/wait保留启动输出与子进程退出信息，不再依赖nohup启动并丢弃全部stderr。
- Java宿主验证独立session，输出阶段与错误；App接受Binder后才将宿主stdio转到/dev/null。关闭ADB后再次校验照片、阅读、控制三个Binder。
- 服务交付只进入raw阶段，复验成功才公开ready及照片/阅读Binder。系统通知、进程输出或收到原始Binder都不能单独把激活标为成功。
- 启动日志有界、脱敏，不包含完整命令、nonce或私钥。旧配对/通知功能和原NFC协议保留。

本机可验证Shell启动语法、引用、HUP继承、输出保留和自动回归，不能执行你手机上的Android16 Binder/SELinux路径。该版改进了流程与启动路径，仍需你安装确认内置服务能否完成交付；若失败，新诊断会给出此前被隐藏的具体阶段。
